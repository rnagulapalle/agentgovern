# AWS connection journey — October 15, 2026

## Product contract

An invited workspace member starts from Connections, selects AWS, saves an account/region scope, discovers AgentCore runtimes through reviewed read-only access, selects a current agent, checks a finite invocation-event window and reviews its accountable owner. The external agent and workflow code stay in AWS. Discovery and owner mapping never create an execution credential, tool grant, approval, provider write or verified enforcement claim.

The first implementation uses the existing CloudInventoryStore, CloudDiscoveryOperations, scoped tenant authentication, private temporary-session binding, invocation projection/reader and CloudOwnerReviewStore. It adds no workflow/state/policy engine and changes no applied migration.

## New server contract

POST `/api/workspace/discovery/activity` takes exactly `connectionId`, `scanId`, `resourceArn`, `version`. It accepts neither credentials, tenant scope, log group, arbitrary time windows nor control flags. Existing workspace authentication, CSRF checks and committed per-connection cloud-check throttling apply. It loads current inventory before and after the bounded AWS read. Revoked access, changed inventory or a different agent/version refuses the result. The API is no-store and request-only.

`LOOPLABS_CLOUD_ACTIVITY_SOURCE_FILE` is a separate administrator-owned private regular JSON file, read by the existing private-file validator. Exact fields: `scope`, `runtimeArn`, `version`, `logGroup`. Scope must match tenant/connection/account/region; the source must match the selected runtime/version and its AgentCore runtime log-group prefix. No browser source selector or ambient credentials are used. Existing `LOOPLABS_CLOUD_DISCOVERY_BINDING_FILE` supplies the short-lived fixed read transport. CloudWatch requests use the reviewed account’s full log-group ARN, so a rotated session cannot redirect a same-named group to another account. No credential issuance, IAM mutation or permission upgrade is performed by the web process.

For the isolated control-demo installation, `LOOPLABS_AWS_CONNECTIONS=enabled` explicitly permits the discovery page and exact AWS inventory, owner review and activity routes through the existing downstream auth. It remains disabled by default; unknown profiles and alternate paths/methods still deny. Azure/Google project operations stay blocked in this installation, and their cards remain Coming soon. This flag does not establish a configured binding, schema, native discovery or action control.

## Test and dogfood plan

- Focused service/HTTP tests: exact input, wrong account/source/version, private-file mode, absent/expired session, stale/retained/missing inventory, throttle, revocation or identity drift during a read, finite paging/deadline, payload exclusion, partial and empty results.
- Mounted component tests with explicitly synthetic API responses: account → inventory → activity → owner review; stable generated reference; no execution endpoint; disabled control enablement; access denial and stale inventory; mobile layout; ignore an earlier agent's late event result after selection changes.
- Installed Next/PostgreSQL/TLS discovery proof: rerun on changed source; keep old receipts. Existing authentic installation receipt must not be relabeled or have its fingerprints rewritten.
- Native dogfood: connect the authorized pilot account in us-west-2 through the installed flow; discover the already deployed runtime; review owner and version. Configure only its reviewed CloudWatch source and minimum read access, then observe a separately authorized trigger. Do not invoke an agent merely to fetch metadata or demonstrate UI.
- Enforcement dogfood is separate: native tool call held, independent decision, automatic continuation, verified effect, changed/expired request denied, uncertain result verified before replay and direct bypass refused. No product claim until all these acceptance checks pass.

## Observed native limitation

A separate read-only diagnostic on the authorized pilot runtime found its DEFAULT CloudWatch log group. A bounded 15-minute first page returned 100 records, all unsupported by the current minimized invocation schema, with more pages available. This is not an empty-activity result or proof of agent failure. Native event-format/source acceptance remains open. Raw application messages were neither saved nor displayed. AWS documents service-provided APPLICATION_LOGS separately from runtime stdout and OTEL logs: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-runtime-metrics.html and https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-get-started.html.
