# Two-company API and execution boundary

October 8, 2026. Local acceptance evidence; not an independent security audit or deployed tenant guarantee.

`pnpm workspace:tenant-proof` starts the real built Next application against a dedicated temporary PostgreSQL schema and the real private HTTP twin. Two companies enroll different customers with identical CRM/email agent IDs and separate member, reviewer, agent and worker credentials. The harness uses authenticated HTTP requests rather than direct route mocks.

Each company sees only its configured catalog, enrollment and saved plans. Sixty-four hostile cross-company reads and approval, execution, reconciliation, pause, submission and grant requests return 403/404 without leaking the other recipient or saved hash. The action-state snapshot remains unchanged and there are no effects. Cross-company record-aware activity routing is also refused.

Two separate real Chromium contexts now sign in through the visible form. Each renders only its company record. Eight additional cross-company API and hostile-Origin approval attempts fail; the session cookie is HttpOnly/Strict and unavailable to page scripts. Expiring each stored session removes API access without effects. This is local HTTP, so the cookie Secure flag under remote HTTPS is not established by this run.

Each company's saved route now runs through its own scoped packaged worker and scheduler, with a distinct task queue on the same local Temporal service. Both histories start with actions held and no effects. Company A's worker receives a confirmed SIGKILL before approval. Each company's own independent reviewer approves exact actions through HTTP; company B completes two effects while A remains active with no effects and its worker remains stopped. A replacement worker then resumes A's original history/actions, including a real lost CRM HTTP response reconciled through readback. The final two CRM/two email effects target only the intended records and recipients. Both actual histories replay without new effects or replacement action identities. The earlier completed-activity retry check is also retained: direct repeated completed calls add no effects.

The application and all packaged worker/scheduler processes now connect as an actual temporary PostgreSQL LOGIN role rather than the migration owner. The harness applies 29 literal GRANT statements from the existing provisioning scripts in its dedicated test schema. The runtime has no table ownership, migration-owner membership, CREATE privilege in that schema, superuser, database/role creation, replication or RLS bypass flags. Provisioning/test database environment values are blanked for these children. Fixture enrollment still uses the separate owner connection; this increment does not prove the complete onboarding experience with that runtime role.

Thirteen direct runtime SQL attacks are refused: saved action hash/payload/company changes, workflow-step and plan-hash rewrites, member/token revocation, action deletion, event mutation/truncation, trigger disabling, replication-mode changes and table creation. Proposal triggers reject otherwise permitted UPDATE attempts; table/column privileges refuse the other operations. The saved action snapshot and provider effects remain unchanged before the browser/API/fault tests. The role still can read both companies' action rows, which is explicitly asserted and recorded as `databaseTenantRls: false`. It also retains the operational UPDATE permissions needed by the application. This is a shared trusted application credential, not isolation from compromised SQL access or a separate approval authority.

The harness starts three worker processes (including the replacement) and two schedulers. This closes a bounded per-company worker-fault isolation check under correctly separated queues. It does not establish noisy-neighbor saturation, misconfigured shared-queue availability, hosted provider tenant authentication or remote operational acceptance. Processes execute the built artifact with its existing integrity check; this increment is packaged-process evidence, not a new Docker or remote TLS trial.

The harness never uses production data, modifies applied migrations, changes release ownership or enables customer integrations. Source-fingerprinted evidence is in `docs/evidence/tenant-isolation-proof.json`. Build the application and worker manifest first. A dedicated `LOOPLABS_TEST_DATABASE_URL`, the FetchSandbox Python runtime, free local ports 3117/8018 and existing dependencies are required. Cleanup confirms process termination and removes its temporary schema/state.

Remaining security acceptance includes broader browser/session attack coverage and remote HTTPS cookie checks, independent review, broader runtime-role and database row-security coverage, tenant quotas and noisy-neighbor load, secure remote operations, SSO/MFA, and provider-side tenant credentials. The private twin's shared test credential and distinct fixture IDs are not real-provider tenant isolation. Application query scoping is not protection against a database owner or compromised global service credential.

Cleanup closes the runtime pool, stops all owned app/provider/worker/scheduler processes, tears down the disposable Temporal service, drops the temporary schema and role grants/role, and removes private fixture files. No production role or applied migration is changed. Provisioner source fingerprints are included so a later permission change requires fresh proof.
